# Векторы движения для FSR 2/3: исследование и прототип

Ветка `proto/motion-vectors` (от `perf/timedemo` 7d5418b). Всё за флагом
`NFSMW_MV=1`, по умолчанию выключено: без флага рендерер рисует как раньше
(вершинные шейдеры читают константы через макрос `CV()`, который
разворачивается в то же выражение, SPIR-V тот же).

## Коротко

- **Векторы движения без исходников игры получить можно, и точные.** Каждый
  draw сцены сопоставляется с тем же draw прошлого кадра (шейдер, буферы
  вершин и индексов, ближайшие константы позиции), вершинный шейдер
  прогоняется второй раз с константами прошлого кадра, разница позиций
  пишется в отдельный аттачмент R16G16F. Это работает одинаково для дороги,
  домов, неба, машины игрока, соперника, колёс: «маска машин» не нужна, у
  каждого объекта свой вектор. В гонке пару находят ~96% draw сцены; у
  остальных (~18 на кадр: частицы, следы — динамические буферы) — векторы
  камеры из глубины.
- **Матрица камеры** — та матрица c0..c3, которую делят больше всего draw
  сцены (мир рисуется в мировых координатах). Камерные векторы перепроекцией
  глубины тоже сделаны, но для машины игрока они дают ошибку перепроекции в
  2.8 раза больше, чем векторы по draw (машина едет вместе с камерой).
- **Точка вставки апскейла найдена**: перед первым тайловым resolve цели сцены
  (цвет RGBA8 b0/pitch 1280 + глубина b1024). После неё — собственная
  пост-обработка игры (блум 320×180, блюры 160×90, композит, который читает и
  цвет 05AA8000, и **глубину** 04FE0000), потом HUD и зеркало.
- **Но энергию на Steam Deck FSR 2/3 не сэкономит.** Сцена — 2.15 мс из ~7.6 мс
  GPU кадра; она упирается в вершины и draw, а не в пиксели: в 0.67 по
  стороне (44% пикселей) она стоит 88% натива. Временной апскейлер стоит
  0.9–1.5 мс (мой однопроходный) и, по оценке, 1–3 мс (FSR 2). Итог прототипа
  в 0.67: GPU кадра 8.4–8.9 мс против 7.6 мс у натива; по PSNR против SSAA он
  к тому же уступает простому пространственному апскейлу из того же 0.67.
- **Рекомендация: FSR 2/3 ради энергии не делать.** Для 5 Вт выгоднее FSR 1
  (уже в работе) и удешевление других проходов, которые вместе дороже сцены:
  resolve карт теней (~1.2 мс), env-куб (~1.5 мс с resolve), отражение
  дороги (~0.5 мс). FSR 2 имеет смысл только как сглаживание (MSAA 4× на
  хосте выключен) — за +1.5–2 мс GPU. Генерация кадров FSR 3 на Deck
  нереалистична (AMD требует ≥60 fps до генерации и RX 6000+).

Внутри сцены: небо (vs_ced640…, перенос в матрице 0 — привязано к камере),
мир (vs_580d1c…, vs_abfb2d…, vs_630d34…, vs_4ad5b4… — часть с общей VP,

bl07060706), спрайты огней (vs_1f555a…, VP×k), частицы quad-list (vs_ef4455…,
vs_93359b…). Позиция у всех: `dot(вход, c0..c3)` (+ c4 = 0).

## Прототип

- `runtime/gpu/shader_translator.cpp`: для вершинного шейдера считается,
  от каких float-констант зависит экспорт позиции (`positionConsts`, поток
  данных по компонентам регистров). MV-вариант (`#define MV`) прогоняет тело
  шейдера дважды (второй раз — `CV()` читает константы прошлого кадра из
  кольцевого буфера, `pc.vfRedirect[0].w`), отдаёт обе клип-позиции (до
  хост-трансформации и джиттера) в locations 16/17; MV-вариант пиксельного
  шейдера пишет `prev/w − cur/w` в аттачмент 3.
- `runtime/gpu/renderer.cpp` (`s_mv`, `MvSceneDraw`, `MvPreviousConstants`,
  `MvFinishScene`): определение draw сцены, цель векторов, сопоставление с
  прошлым кадром, голосование VP, джиттер Halton(2,3) через `posScale`
  только для draw сцены (не HUD, не пост-обработка), сжатие сцены в угол
  целей при `NFSMW_MV_SCALE<1` (только для оценки — в продакшене это
  render_scale ниже 1× из работы над FSR 1), апскейлер в начале первого
  resolve сцены, копия результата в цель сцены и глубины (через буфер:
  RADV не умеет blit D32S8).
- `runtime/gpu/taau_glsl.h`: апскейлер-заменитель FSR 2 с теми же входами
  (Lanczos-2 текущего кадра, вектор ближайшей глубины 3×3, история
  Catmull-Rom с клиппингом в YCoCg), режимы отладки.
- `runtime/gpu/motion_vectors.h`, `tests/motion_vectors_test.cpp`: джиттер,
  матрицы, сопоставление draw, голосование камеры.
- `scripts/mv_eval.py`: PSNR шотов timedemo против эталона по зонам (машина
  игрока, дорога, остальное; HUD маскируется).

Переменные: `NFSMW_MV=1`; `NFSMW_MV_SCALE` (0.5–1); `NFSMW_MV_MODE=camera|none`;
`NFSMW_MV_JITTER=0`; `NFSMW_MV_FEEDBACK`; `NFSMW_MV_DEBUG=1` (векторы
цветом) / `2` (ошибка перепроекции); `NFSMW_MV_LOG=1`;
`NFSMW_MV_DUMP=<кадр>[,n]` (все draw и resolve кадра с константами позиции).

## Оценка

Steam Deck OLED, записанная гонка `~/sb-bench/race.jlg`, реплей в темпе

### Точность векторов: ошибка перепроекции

Прошлый кадр, сдвинутый векторами, против текущего (`NFSMW_MV_DEBUG=2`,
натив, без джиттера и без накопления): среднее картинки ошибки ×4 после
пост-обработки игры (0–255, меньше — лучше) и доля пикселей с ошибкой > 32;
среднее по 7 шагам, HUD маскирован.

| векторы | кадр | машина игрока | дорога | остальное |
|---|---|---|---|---|
| по draw (прототип) | **25.9** / 17.5% | **39.6** / 27.1% | **40.0** / 27.6% | 14.7 / 9.5% |
| только камера (глубина) | 37.8 / 22.3% | 110.3 / 61.6% | 45.1 / 28.7% | 11.7 / 7.0% |
| нет | 41.0 / 30.0% | 40.9 / 30.0% | 68.1 / 52.2% | 27.4 / 18.9% |

Векторы по draw лучше всего в кадре в целом и на машине. Векторы камеры
для машины игрока непригодны (она едет вместе с камерой: ошибка ×2.8) — это и
есть задача «маски машин», которую сопоставление draw решает без маски.
Остаток ошибки — пересэмплирование алиасных кромок, блики и отражения,
зависящие от взгляда (кузов, мокрый асфальт), тень машины на дороге (тень
едет с машиной, дорога — нет) и частицы. Картинка:
[reprojection-error-4800.jpg](mv-eval/reprojection-error-4800.jpg) (слева
направо: по draw, камера, нет). Сами векторы цветом:
[vectors-debug.jpg](mv-eval/vectors-debug.jpg) (машина однотонная — ноль
относительно камеры; дорога и дома — радиальное расширение от точки схода).

### Качество апскейла: PSNR против SSAA, дБ (среднее по 7 шагам)

| режим | кадр | машина | дорога | остальное |
|---|---|---|---|---|
| натив 1280×720 (как сейчас) | **36.20** | **37.32** | **42.21** | **37.80** |
| TAA 1× (джиттер + векторы) | 34.79 | 34.98 | 36.98 | 37.46 |
| пространственный 0.67 (Lanczos, без истории) | 34.14 | 34.31 | 36.54 | 36.40 |
| TAAU 0.67, векторы по draw | 32.74 | 32.40 | 33.79 | 36.14 |
| TAAU 0.67, векторы камеры | 32.40 | 31.57 | 33.58 | 34.90 |
| TAAU 0.67, без векторов | 29.79 | 29.72 | 30.56 | 31.94 |
| TAAU 0.5, векторы по draw | 31.42 | 30.98 | 32.11 | 35.11 |

- Порядок «по draw > камера > нет» держится во всех зонах: на машине
  +0.8 дБ к камерным, +2.7 дБ к отсутствию векторов.
- Шлейфы: с векторами по draw на машине игрока и сопернике шлейфов нет; с
  векторами камеры раздваиваются задние фонари и стойки антикрыла машины
  игрока и колёса соперника; без векторов полосит всё
  ([player-car-4800.jpg](mv-eval/player-car-4800.jpg),
  [opponent-4900.jpg](mv-eval/opponent-4900.jpg),
  [opponent-4600.jpg](mv-eval/opponent-4600.jpg),
  [signs-4800.jpg](mv-eval/signs-4800.jpg); порядок: эталон, натив, TAA 1×,
  пространственный 0.67, TAAU 0.67 по draw, камера, без векторов, TAAU 0.5).
- Временное накопление по PSNR проигрывает пространственному апскейлу из
  того же 0.67 (−1.4 дБ): в гонке всё время большое движение (дорога — десятки
  пикселей за кадр), каждое пересэмплирование истории мылит асфальт и
  разметку. Клиппинг истории не даёт шлейфов, но и накопить деталь не даёт.
  Это свойство моего заменителя FSR 2, а не векторов; у FSR 2 (locks,
  Lanczos-история) мыла меньше, но быстрое движение — его же слабое место.
  PSNR одиночных кадров не видит главного выигрыша TAA — стабильности кромок
  во времени (у натива 1 сэмпл, кромки «ползут»); это надо смотреть видео.

### Цена на GPU и CPU

GPU-время проходов кадра 7698 (`NFSMW_PASS_PROFILE`, мкс; апскейлер —
отдельные записи профиля):

| | натив | MV, 1× | MV, 0.67 |
|---|---|---|---|
| тени (2×1600²) + их resolve | 352 + ~1200 | так же | так же |
| отражение дороги 640×360 | 470 | так же | так же |
| env-куб, 6 граней 256² | ~910 | так же | так же |
| **сцена** | **2154** | 2483 | 1906 |
| апскейлер (compute 1280×720) | — | 1502 (Lanczos) / 920 (Гаусс) | 1528 / 922 |
| копия выхода в цель сцены | — | 82 | 79 |
| глубина до 1280×720 (буфер) | — | — | 228 |
| пост-обработка игры (композит 350) | ~570 | ~570 | ~570 |
| **всего за кадр** (проходы + между ними) | **7605** | 10322 | 8904 |

Среднее GPU busy за окно (`summary.json`, мс/кадр): натив 11.07; TAA 1×
12.68; TAAU 0.67 12.21; TAAU 0.5 11.74. Командный процессор (CPU): 7.31 →
~8.4 мс/кадр (сопоставление draw и вторая порция констант).

- Сцена упирается в вершины и draw, а не в пиксели: в 0.67 (44% пикселей)
  она стоит 88% натива, причём MV-вариант VS (двойной прогон) добавляет
  ~0.3 мс. Без него экономия сцены в 0.67 — порядка 0.5–0.6 мс.
- Временной апскейлер стоит 0.9–1.5 мс (мой, один проход); FSR 2 — несколько
  проходов, по таблицам AMD 0.6–1.3 мс на 1080p на RX 6650 XT / RX 590, на
  Deck при 720p по оценке 1–3 мс.
- Итого FSR 2 при 0.67 даст +0.5…+2 мс GPU к нативу, а не экономию. Для
  энергии это шаг назад.

## Объём работ до продакшена (FSR 2)

Если всё же делать FSR 2 (как сглаживание или когда сцена станет
пиксельно-ограниченной, например при внутреннем разрешении выше 1×):

1. FSR 2 из FidelityFX SDK v1.1.4 (MIT; FSR 2.3.3 / 3.1.4 с Vulkan-бэкендом;
   SDK 2.x — только DX12). Шейдеры собрать glslang на Linux вместо
   `FidelityFX_SC.exe` (так делают Godot и форки), поправить `abs(float)` в
   `lanczos2()` под clang (issue #129). 3–5 дней.
2. Векторы без двойного прогона VS: для шейдеров с позицией = одна матрица
   (почти все в сцене) передавать на draw матрицу
   `M = WVP_prev · WVP_cur⁻¹` и считать prev из текущей клип-позиции; двойной
   прогон оставить для остальных. 2–3 дня.
3. Reactive / transparency mask из состояния смешивания (частицы, искры,
   стёкла, спрайты огней, блик солнца). 1–2 дня.
4. Перейти на render_scale ниже 1× из работы над FSR 1 вместо сжатия сцены
   через posScale (глубина, ZPD, resolve — там). 2–3 дня после FSR 1.
5. Сброс истории на смене камеры (скачок VP: заставки, повторы), реверс,
   пауза/меню; HUD и зеркало уже вне сцены. 1–2 дня.
6. Прогрев пайплайнов MV-вариантов (ключ пайплайна уже различает их битом
   `pad`), удешевление сопоставления на CPU (+1.1 мс CP сейчас), проверки на
   macOS/iOS (MoltenVK: locations 16/17), ultrawide/Vert+, внутреннее
   разрешение > 1×. 3–5 дней.
7. Замеры качества с видео (временная стабильность), энергии на Deck. 2–3 дня.

Итого ~3–4 недели одного разработчика до продакшен-качества.

## Рекомендация

**FSR 2/3 не делать** — ради энергии точно. Векторы движения в этой игре
получить можно и надёжно (прототип это показал: по draw, без маски, без
исходников), но на Steam Deck сцена — четверть GPU-кадра и упирается в
вершины, так что временной апскейл стоит дороже, чем экономит. Для 5 Вт
выгоднее FSR 1 (уже в работе) и проходы, которые сейчас дороже, чем
выигрыш от любого апскейла: resolve карт теней (~1.2 мс: сэмплировать
глубину из render target без resolve и обратного untile), env-куб (~1.5 мс
с resolve: 2 грани за кадр по кругу или 128²), отражение дороги (~0.5 мс:
половинное разрешение), барьеры и простои между проходами (~3 мс
«между проходами» на кадр). FSR 2 как режим сглаживания (вместо
выключенного MSAA 4×) — возможен позже, на мощных машинах, за +1.5–2 мс GPU;
наработки ветки (поиск VP, сопоставление draw, MV-варианты шейдеров, точка
вставки) для этого пригодятся. Генерацию кадров FSR 3 не рассматривать
(≥60 fps до генерации, RX 6000+, прокси-swapchain).
